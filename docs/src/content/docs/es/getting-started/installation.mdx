Pyzed necesita **Python 3.10 o superior**.

## Desde PyPI

<Commands
	uv={`
		uv add pyzed-ui          # en un proyecto de uv
		uv run python main.py
	`}
	pip={`
		{venv}       # una vez por proyecto
		{activate}
		pip install pyzed-ui
		python main.py
	`}
	python={`
		{py} -m pip install pyzed-ui
		{py} main.py
	`}
/>

- **uv** gestiona el proyecto por ti: [Crear un proyecto](/pyzed/es/getting-started/new-project/) empieza una app
  nueva así, y es lo que usa el resto de esta documentación. Instálalo desde
  [docs.astral.sh/uv](https://docs.astral.sh/uv/).
- **pip** instala en un *entorno virtual* (`.venv`), una carpeta que separa los paquetes de este proyecto del resto
  de tu equipo. Actívalo en cada terminal nueva antes de ejecutar tu app.
- **python** instala en el Python de tu equipo, sin nada más que aprender. En Windows, `py` es el lanzador de
  Python que trae el instalador de [python.org](https://www.python.org/downloads/); en macOS y Linux el comando
  suele ser `python3`.

El paquete se llama `pyzed-ui` en PyPI (el nombre `pyzed` ya estaba ocupado), pero se importa como `pyzed`.
Los wheels precompilados para Linux, macOS y Windows incluyen el motor de Rust, así que no
necesitas compilar nada.

<Aside type="note" title="Solo wheels precompilados">
En PyPI solo hay wheels, compilados y probados por el pipeline de releases para Linux (x86_64 y ARM, glibc y
musl), macOS (Intel y Apple Silicon) y Windows (x64 y ARM). Un mismo wheel sirve para cualquier Python desde
3.10. En otra plataforma la instalación se detiene con un error en lugar de compilar; ahí instala desde el
código fuente (abajo).
</Aside>

## Desde el código fuente

<Commands

	python={`{py} -m pip install git+https://github.com/albakore/pyzed`}

Esto compila la extensión de Rust, así que necesitas [Rust 1.88 o superior](https://rustup.rs) (`rustup update` actualiza uno más antiguo) y las
dependencias de sistema de tu plataforma:

## Desarrollar Pyzed

Para trabajar en Pyzed, clona el repositorio. Necesitas [Rust 1.88 o superior](https://rustup.rs) (`rustup update` actualiza uno más antiguo) y las
dependencias del sistema de arriba.

<Commands
	uv={`
		git clone https://github.com/albakore/pyzed
		cd pyzed
		uv sync                          # crea .venv, compila el núcleo de Rust (release) e instala pyzed editable
		uv run pytest tests
		uv run python examples/gallery.py
	`}
	pip={`
		git clone https://github.com/albakore/pyzed
		cd pyzed
		{venv}
		{activate}
		pip install maturin pytest
		maturin develop --release        # repítelo después de cambiar código de Rust
		pytest tests
		python examples/gallery.py
	`}
/>

- `uv sync` también instala el grupo `test` (maturin y pytest). La primera compilación tarda unos minutos.
- Los cambios en Python (`python/pyzed/`) se usan directamente.
- Con uv, el siguiente `uv run` o `uv sync` después de cambiar código de Rust (`src/`) recompila el núcleo solo; con
  pip, vuelve a ejecutar `maturin develop --release`. Usa `--release`: la build de depuración es mucho más lenta al
  usar la ventana.
- `uv sync --extra designer` añade ty y ruff para el editor de código del diseñador.
- En Linux, una build desde el código no suena por defecto, así que compila sin paquetes extra del sistema:
  `pyzed.audio` renderiza offline y con su reloj silencioso. Para dispositivos de audio y MIDI, instala las
  cabeceras de ALSA (`sudo apt install libasound2-dev pkg-config`; Fedora: `sudo dnf install alsa-lib-devel`)
  y compila con `maturin develop --release --features alsa` (con uv, deja exportado `MATURIN_PEP517_ARGS="--features alsa"` y ejecuta `uv sync --reinstall-package pyzed-ui`).

## Linux y WSL

Pyzed ajusta algunas cosas antes de abrir la primera ventana:

- **Silencia los avisos del driver de la GPU.** Mesa imprime mensajes como `libEGL warning:
  failed to get driver name for fd -1` o `MESA: error: ZINK: failed to choose pdev` mientras el
  renderer busca un backend que funcione. No afectan a nada, así que Pyzed define
  `EGL_LOG_LEVEL=fatal` y `MESA_LOG=null`. Con `PYZED_GPU_LOGS=1` vuelven a aparecer.
- **En WSL usa X11.** El compositor Wayland de WSLg corta la conexión al maximizar o
  redimensionar una ventana, y eso imprime `Io error: Broken pipe (os error 32)`. En WSL, Pyzed
  usa X11 (a través de XWayland). Con `PYZED_WAYLAND=1` se mantiene Wayland.
- **En WSL abre las páginas en el navegador de Windows.** WSL no suele tener navegador propio,
  así que los inicios de sesión (los de los agentes de IA), la documentación y los demás enlaces
  se abren en tu navegador predeterminado de Windows. Las páginas que vuelven a Pyzed en
  `127.0.0.1` siguen llegando gracias al reenvío de localhost de WSL. Los programas que necesitan
  una terminal, como el inicio de sesión de Claude Code, se abren en Windows Terminal (o en una
  consola) dentro de tu distribución de WSL. Con `BROWSER` eliges el navegador tú.

Las variables que definas tú (`EGL_LOG_LEVEL`, `MESA_LOG`, `WAYLAND_DISPLAY`, `BROWSER`...) nunca se tocan.

## WSL: ventanas nativas de Windows

En WSL, Pyzed abre cada ventana **como un programa nativo de Windows**, no a través de WSLg: `pyzed design`,
`pyzed run`, `pyzed dev`, tus scripts que llaman a `pz.run`, Ejecutar en Pyzed Design y las vistas en vivo de los
agentes de IA. La ventana es una ventana de Windows de verdad, dibujada con los drivers de GPU de Windows, así que
va más rápida y se acopla, escala y aparece en la barra de tareas como cualquier otra aplicación. Tu código y tu
proyecto siguen en WSL: sigues editando en Linux (en Zed, por ejemplo) y la recarga en caliente recoge cada
guardado.

Solo necesita [uv en Windows](https://docs.astral.sh/uv/getting-started/installation/). Pyzed puede instalarlo por
ti, desde WSL:

```bash
uv run pyzed windows setup     # instala uv en Windows si falta y prepara el proyecto
uv run pyzed windows           # muestra qué se usa y dónde
```

Cómo funciona:

- Windows lee el proyecto a través de `\\wsl.localhost\<distribución>\...` y arranca en la misma carpeta.
- Windows tiene **su propio entorno**, en `%LOCALAPPDATA%\pyzed\wsl\`, con la misma versión de Python, las
  dependencias del proyecto en las versiones de `uv.lock` y la wheel de `pyzed-ui` de la misma versión (siempre
  una wheel ya compilada: en Windows no se compila nada). El `.venv` del proyecto sigue siendo el de Linux. Se crea
  la primera vez (unos segundos) y de nuevo solo cuando cambian las dependencias.
- El comando en WSL espera a la ventana: su salida, la consola de Pyzed Design y el código de salida son los de la
  aplicación, y al detenerlo (Detener, <kbd>Ctrl</kbd>+<kbd>C</kbd>) la ventana se cierra.

Sin uv (ni el lanzador `py` de Python) en Windows, las ventanas se abren por WSLg como antes, con un aviso que
explica cómo prepararlo. Para usar siempre WSLg, define `PYZED_WINDOWS=0` o añade `--wslg` a `pyzed design`, `run`
o `dev`.

| Variable | Qué hace |
| --- | --- |
| `PYZED_WINDOWS=0` | Abre las ventanas por WSLg. |
| `PYZED_WINDOWS_ENV=NOMBRE,NOMBRE` | Más variables para la aplicación en Windows (claves de API...). Las `PYZED_*` siempre pasan. |
| `PYZED_WINDOWS_WHEEL` | Ruta o URL de la wheel de `pyzed-ui` para Windows (ver abajo). |

:::note[Si trabajas en Pyzed]
Un checkout de Pyzed (`uv sync` en el repositorio) está compilado para Linux, y puede que su versión aún no esté
publicada, así que la ventana de Windows usa la última versión publicada de `pyzed-ui`. Para probar tus cambios en
Windows, descarga la wheel de Windows que CI compila para tu rama (o la de una release) y apunta
`PYZED_WINDOWS_WHEEL` a ella.
:::

## Comprobar la instalación

<Commands
	uv={`
		uv run python -c "import pyzed; print(pyzed.__version__)"
		uv run pyzed icons folder
	`}
	pip={`
		python -c "import pyzed; print(pyzed.__version__)"
		pyzed icons folder
	`}
	python={`
		{py} -c "import pyzed; print(pyzed.__version__)"
		{py} -m pyzed icons folder
	`}
/>

La primera línea muestra la versión; la segunda, los nombres de iconos que contienen "folder".
